# claude-workflow

A local Claude Code marketplace hosting one plugin, `staff`, a staff-AI-engineer workflow.
Run `scripts/setup.sh` to register the marketplace and install the plugin, then run `gh auth login`.
Setup also installs the review and security tools the router uses: claude-security, the Trail of Bits plugins sharp-edges, supply-chain-risk-auditor and insecure-defaults (marketplace pinned to a commit), and gitleaks 8.19+ for the secret scan. Set `STAFF_OUTPUT_STYLE=Explanatory` (or `Learning`) when running it to turn on teach mode for every repo.
Per client repo, run `scripts/stack.sh --dry-run <repo>`, then `scripts/stack.sh <repo>`: it detects the repo's dependencies, offers the matching skills from `stacks/manifest.tsv`, installs the accepted ones at local scope, and git-excludes what it writes plus the workflow files `/staff:build` needs ignored (the router only checks them). It also offers the Bash sandbox for the repo (default yes; writes to `.claude/settings.local.json`): sandboxed commands may write only the directory Claude Code starts in, temp, the staff state directory and uv's cache, and PyPI and GitHub are pre-allowed while other hosts prompt. It also pins `autoAllowBashIfSandboxed` to false unless already set, since Claude Code before 2.1.324 defaulted it to true. The sandbox covers Bash and its child processes only, and it limits writes, not reads: a sandboxed command can still read your GitHub token and reach GitHub. In a linked worktree, Claude Code prefers the main checkout's `.claude/settings.local.json`; `stack.sh` warns if that file sets the sandbox too. `scripts/stack.sh --self-test` checks its detection, the manifest pins and the sandbox settings.
The trivial tier runs the gate, `plugins/staff/scripts/staff_gate.py`, configured per repo by a git-excluded `.staff-gate.toml` (example in `templates/python/`). Its tests build throwaway fixture repos: `uv run --python 3.11 --with pytest --with pytest-cov pytest tests/gate -q`.
Run `scripts/setup.sh` from a dedicated clean clone checked out on `main` (or a tag), and do workflow development in a different clone. The installed `staff` plugin runs from the checkout that setup.sh registered, so whatever branch is checked out there is live in every client session.
